## 修正：视觉能力误判（用户反馈"好几个支持图片但前端说都不支持"）
- 真因：`ollamaModelVision` 只查 `model_info["vision"]`，而 Ollama 该字段**实际不存在**；名称启发式又匹配不到自定义名（turbo/qwen3.8-mlx 等），全部误判 false。
- 实测该 Ollama(0.6+) `/api/show` 返回 **`capabilities` 数组**，四个模型全是 `["completion","vision","tools","thinking"]` → 这才是权威信号。
- 修复：`ollamaModelVision` 改为①优先解析 `capabilities` 含 "vision"（非空且不含=明确不支持，不再走启发式）②老版本无 capabilities 时看 `projector_info` 非空 ③再看 `model_info.vision` ④最后名称启发式。
- 修复后 `/api/chat-plus/models` 四个模型 vision 全部 True；用 96x96 白底红圆生成图实测 `qwen3.8:27b-mlx` 回复"红色圆形"，前端→后端→Ollama 多模态链路完全打通。已 docker commit 固化。
- 注意：Ollama 主机只能从容器内访问（host 沙箱 curl 不通），排查/测试需 `docker exec devtools curl ...` 或经 8082 后端。

## 加固：图片上下文硬上限（用户追问"会不会爆上下文"）
- 查实各模型上下文：`turbo`/`nex-n2.5-mini` 显式 `num_ctx 16384`(16K)；`qwen3.8:27b-mlx` 无 num_ctx 走默认；三者 `model_info.*.context_length` 均 262144（理论上限≠实际用）。
- 结论：仅靠压缩不构成硬保证（多轮图片会累积）。改为双保险：
  1. 压缩更狠：`IMG_MAX_DIM 1024`（原1280）、`IMG_QUALITY 0.8`（原0.82）；`MAX_IMAGES 4`（原6）。
  2. `buildPayloadMessages` 新增**单次请求图片总预算 `IMG_TOTAL_BUDGET=4`**：从最新消息往回取，总量≤4，更早的图片整组丢弃并替换为文字占位「（此前的图片已省略以节省上下文）」——彻底杜绝多轮图片累积爆上下文。
  3. `imageContextWarn` 阈值 2500→1200KB。
- 估算：4 张 1024px 图 ≈ 5.5K 视觉 token + 文本，16K 上下文模型可从容容纳。
- 部署：前端 build + HOT_DEPLOY；验证 health 200、bundle 含占位文案、vision 全 True（后端随镜像保留）、ocr/asr/redis healthy。

## 修复：出图进度永远是「排队中 1%」（client_id 不匹配）+ 端到端跑通
- 现象：任务在 ComfyUI 里确实在采样，但我们后端任务表 phase 一直停在「排队中」、progress=1，前端进度条像卡死；查 `/queue` 能看到 prompt 在 queue_running，`/history` 只在结束时才有。
- 根因：`queuePrompt` 提交时带 `client_id: "devtools-aichat"`，而 `watchProgress` 的 ws 用 `?clientId=devtools-aichat-progress`。ComfyUI 把 execution_start/executing/progress 事件**按 client_id 定向投递**，两边不一致 → 事件发给了没人监听的 sid。用独立 ws 探针（`/tmp/wsdump`）验证：只收到一条 `status`，25s 内零 progress。
- 修复：抽 const `comfyClientID = "devtools-aichat"`，`/prompt` 的 `client_id` 与 `/ws?clientId=` 共用；另外 `comfyExecutionError` 识别 `execution_interrupted`（被 interrupt 不再报「未返回详细原因」，改报「任务被中断」），并补单测。
- 验证：修后同一任务进度 5%→27%→50%→72%→100%，8 步 @768 用时 50s，成品 PNG 2.5MB→768x768 落盘 `/api/chat/uploads/ai/YYYYMMDD/xxx.png` HTTP 200。已 `docker cp` + restart + commit 固化。
- 已实测成功：用户在 15:36 从浏览器提交的 t2i 任务（prompt 41370239）在 15:41 success，图 1024x1024 落盘 `7f04dd913cebbe1e02583c0f.png`。
- 注意：ComfyUI `POST /interrupt` 会中断当前任务；排查时别乱调，会打断用户任务。Qwen-Image 首次跑要加载 ~13GB GGUF，前半分钟无事件属正常。


## 弱网加固 + /ai-chat 异步任务化（断线续传 / 刷新恢复）
- 用户诉求：外网/弱网请求易失败；要异步处理；刷新重进能拿到成功结果，失败也要知道原因。
- 第一层（服务端↔上游，同步重试仍需保留）：新增 `handlers/ai_gateway_net.go`
  - `outboundRetryPolicy`（默认 4 次尝试、250ms 起指数退避+抖动、总预算 120s、流式静默 120s、拨号 10s），由 `ai_gateway.retry` 配置覆盖并夹紧。
  - `isTransientConnErr` 扩展到 EOF/UnexpectedEOF/ECONNABORTED/ENETUNREACH/EHOSTUNREACH/ETIMEDOUT/DNS 抖动；仍排除 context.Canceled/DeadlineExceeded。
  - `readResponseBody` 不再吞 ReadAll 错误（旧代码 `respBody, _ := io.ReadAll` 会把截断 body 当成功，只报 JSON 解析失败且不重试）。
  - `stallGuard`：SSE 无总超时，靠"零字节静默"判定断流 → cancel 上游 + 回 error 帧（`upstream_stalled`），不再让前端对着心跳无限等。
  - transport：KeepAlive 15s / IdleConnTimeout 45s / MaxConnsPerHost 32（弱网 NAT 下少复用半死连接）。
- 第二层（客户端↔服务端，任务化）：`models/chat_plus_task.go` + `handlers/chat_plus_task.go`
  - SQLite 表 `chat_plus_tasks`（id/conversation_id/model/status/content/reasoning/error_message/seq/时间戳），`RegisterInit` 注册。
  - 接口：`POST /api/chat-plus/tasks`(202)→`GET /tasks/:id`→`GET /tasks/:id/stream?from=<seq>`（先订阅再回放，id: 行=续传游标）→`POST /tasks/:id/stop`→`GET /tasks?conversation_id=`（刷新对齐）。原 `/chat/stream` 保留兼容。
  - 复用同步流实现：`runChatPlusStream` 抽出，任务 runner 用 `chatTaskSink`（实现 gin.ResponseWriter）把输出写进内存缓冲，既有 `streamOpenAICompatibleWithClient`/`streamMiniMaxChat` 一行未改。
  - 进度每 2s 落库；启动时 `FailStaleChatPlusTasks` 把上次遗留 running 标失败（否则永远转圈）；并发上限 8；内存缓冲 64 个/30min TTL/单任务 1MB。
  - 上游错误体经 `cleanUpstreamError` 压成一句人话；`[DONE]` 去重。
- 前端 `AIChatTool.vue`：发送改为建任务+订阅；断线按 `from=seq` 自动续传（600ms 起退避，连续 4 次失败降级为轮询快照）；`finalizeStream` 按 convId 归档（切会话不串）；挂载恢复上次会话（`chat-plus-current-conv`）+ `reconcileChatTasks` 补成功/失败消息；失败显示原因并可「重试」；停止会调 stop 接口；「重新生成」把旧 taskId 记入 `chat-plus-hidden-tasks-*` 防重复补回。
